Tema 4

4. Concurrencia

La concurrencia es la capacidad de un sistema gestor de bases de datos (SGBD) para ejecutar varias transacciones al mismo tiempo sobre los mismos datos. Intercalar operaciones aprovecha mejor el procesador y los discos, reduce el tiempo de respuesta y permite atender a muchos usuarios a la vez; sin embargo, sin control, ese intercalado produce resultados incorrectos.

El criterio de corrección más aceptado es la serializabilidad: una ejecución concurrente es correcta si su efecto es equivalente al de alguna ejecución en serie de las mismas transacciones (Silberschatz et al., 2020). Para garantizarlo, el SGBD utiliza un gestor de concurrencia que aplica dos grandes familias de técnicas: los protocolos basados en bloqueos y el control de concurrencia multiversión (MVCC).

Transacciones simultáneas

Varias secuencias de lecturas y escrituras se intercalan en el tiempo y compiten por los mismos registros.

Serializabilidad

La ejecución intercalada debe producir el mismo resultado que alguna ejecución una tras otra.

Bloqueos

Una transacción reserva un dato con bloqueo compartido (lectura) o exclusivo (escritura) antes de usarlo; las demás esperan.

Multiversión (MVCC)

Se conservan varias versiones de cada fila; cada transacción lee una instantánea consistente y los lectores no bloquean a los escritores.

Tema 4.1

4.1 Conceptos

Antes de estudiar los mecanismos de control conviene precisar dos conceptos básicos y los problemas que aparecen cuando las transacciones se intercalan sin protección.

Transacción

Unidad lógica de trabajo formada por una secuencia de operaciones de lectura y escritura que debe ejecutarse completa o no ejecutarse. Comienza con BEGIN y termina con COMMIT (confirmación) o ROLLBACK (aborto). Ejemplo: transferir dinero implica restar de una cuenta y sumar a otra.

Planificación (schedule)

Orden cronológico en que se ejecutan las operaciones de varias transacciones. Es serial si cada transacción termina antes de que empiece la siguiente, y serializable si, aun intercalada, es equivalente a una planificación serial (Elmasri y Navathe, 2016).

T1: R(A)  W(A)            R(B)  W(B)  COMMIT
T2:             R(A)  W(A)                    COMMIT

Problemas de la concurrencia sin control

Lectura sucia

T2 lee un valor que T1 modificó pero no ha confirmado. Si T1 hace rollback, T2 trabajó con un dato que nunca existió oficialmente.

Lectura no repetible

T1 lee una fila dos veces y obtiene valores distintos porque, entre ambas lecturas, T2 la actualizó y confirmó.

Lectura fantasma

T1 repite una consulta con condición (por ejemplo, WHERE saldo > 1000) y obtiene un conjunto distinto de filas porque T2 insertó o eliminó registros que cumplen la condición.

Actualización perdida

T1 y T2 leen el mismo valor, ambas lo modifican y la última escritura sobrescribe a la primera: el cambio de una transacción desaparece.

Tema 4.2

4.2 Propiedades de las transacciones (ACID)

El acrónimo ACID, propuesto por Haerder y Reuter (1983), resume las cuatro garantías que todo SGBD transaccional debe ofrecer. Selecciona cada propiedad para ver su definición, el mecanismo con el que el gestor la implementa y un ejemplo.

Atomicidad

Definición. La transacción es indivisible: se aplican todas sus operaciones o ninguna. Nunca queda un resultado parcial en la base de datos.

Mecanismo del gestor. El subsistema de recuperación registra en el log (bitácora) las imágenes anteriores de los datos; ante un error o un ROLLBACK, deshace (UNDO) los cambios incompletos.

Ejemplo. En una transferencia de $500, si el sistema falla después de restar a la cuenta A y antes de sumar a la cuenta B, el gestor revierte la resta.

Consistencia

Definición. Una transacción lleva la base de datos de un estado válido a otro estado válido, respetando todas las reglas de integridad definidas.

Mecanismo del gestor. Verificación de restricciones (PRIMARY KEY, FOREIGN KEY, UNIQUE, CHECK, NOT NULL) y disparadores; si alguna falla, la sentencia o la transacción se rechaza. La lógica de negocio correcta es responsabilidad del programador.

Ejemplo. Con CHECK (saldo >= 0), un retiro que deje el saldo en negativo se rechaza y la base conserva su estado válido.

Aislamiento

Definición. Las transacciones concurrentes no deben ver los efectos intermedios de las otras; cada una se comporta como si se ejecutara sola.

Mecanismo del gestor. El gestor de concurrencia aplica bloqueos (protocolo 2PL) o instantáneas multiversión (MVCC). El grado exacto se regula con el nivel de aislamiento (tema 4.4).

Ejemplo. Mientras T1 transfiere dinero, una consulta de T2 que suma los saldos no ve la cuenta A ya descontada y la cuenta B aún sin abonar.

Durabilidad

Definición. Una vez que la transacción hace COMMIT, sus cambios permanecen aunque ocurra una caída del sistema, un corte de energía o un fallo del software.

Mecanismo del gestor. Registro de escritura anticipada (Write-Ahead Logging, WAL): el log se escribe en disco antes de confirmar; tras un fallo, el gestor rehace (REDO) las transacciones confirmadas. Se complementa con respaldos y réplicas.

Ejemplo. Si el servidor se apaga un segundo después de confirmar un pago, al reiniciar el pago sigue registrado.

Tema 4.3

4.3 Grados de consistencia

Gray et al. (1976) definieron cuatro grados de consistencia según qué tanto una transacción se protege de las demás. Cada grado incluye las garantías del anterior y se obtiene con una disciplina distinta de bloqueos. Un bloqueo es corto si se libera al terminar la operación y largo si se mantiene hasta el fin de la transacción.

Bloqueo compartido (S)

Se solicita para leer. Varias transacciones pueden tener S sobre el mismo dato, pero ninguna puede escribirlo mientras existan.

Bloqueo exclusivo (X)

Se solicita para escribir. Solo una transacción puede tenerlo y es incompatible con cualquier otro bloqueo S o X.

  1. 0

    Grado 0

    La transacción no sobrescribe datos sucios de otras. Usa bloqueos X cortos al escribir y no bloquea lecturas. Es el nivel mínimo y no evita actualizaciones perdidas.

  2. 1

    Grado 1

    Grado 0 + sus escrituras no se confirman antes del fin de la transacción. Usa bloqueos X largos; evita la actualización perdida, pero aún permite lecturas sucias.

  3. 2

    Grado 2

    Grado 1 + no lee datos sucios. Añade bloqueos S cortos en las lecturas; evita la lectura sucia, pero permite lecturas no repetibles. Equivale aproximadamente a Read Committed.

  4. 3

    Grado 3

    Grado 2 + otras transacciones no modifican lo que esta leyó hasta que termine. Usa bloqueos S y X largos: lecturas repetibles y ejecución serializable. Equivale a Serializable.

Bloqueo en dos fases (2PL)

Protocolo que garantiza la serializabilidad por conflictos. Cada transacción pasa por una fase de crecimiento, en la que solo adquiere bloqueos, y una fase de decrecimiento, en la que solo los libera; después de liberar uno, ya no puede pedir otro. En la variante 2PL estricto, los bloqueos X se mantienen hasta el COMMIT o ROLLBACK, lo que evita aborts en cascada. Su principal costo es la posibilidad de interbloqueos (deadlocks), que el gestor detecta y resuelve abortando una de las transacciones.

Tema 4.4

4.4 Niveles de aislamiento

El estándar SQL define cuatro niveles de aislamiento según las anomalías que se permiten. A mayor aislamiento, mayor protección, pero también menor concurrencia y más esperas o reintentos. Berenson et al. (1995) mostraron que esta definición basada en anomalías es incompleta y motivaron el estudio de niveles como el aislamiento por instantáneas.

-- Seleccionar el nivel de una transacción
BEGIN;
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;
-- ... operaciones ...
COMMIT;

Nivel 1

Read Uncommitted

Permite leer cambios no confirmados. Máxima concurrencia, mínima protección.

Nivel 2

Read Committed

Cada sentencia ve solo datos confirmados antes de empezar. Predeterminado en PostgreSQL, Oracle y SQL Server.

Nivel 3

Repeatable Read

Las filas leídas no cambian durante la transacción. Predeterminado en MySQL InnoDB.

Nivel 4

Serializable

Resultado equivalente a una ejecución en serie. Puede abortar transacciones que deben reintentarse.

¿Qué anomalías son posibles en cada nivel? (estándar SQL)
Nivel de aislamientoLectura suciaLectura no repetibleLectura fantasma
Read UncommittedPosiblePosiblePosible
Read CommittedEvitadaPosiblePosible
Repeatable ReadEvitadaEvitadaPosible*
SerializableEvitadaEvitadaEvitada

* Permitida por el estándar; PostgreSQL la evita en este nivel (ver nota).

Nota sobre PostgreSQL

PostgreSQL implementa los niveles con MVCC. Su Repeatable Read usa una instantánea tomada al inicio de la transacción, por lo que también evita las lecturas fantasma, algo que el estándar no exige. Además, trata Read Uncommitted como Read Committed: nunca permite lecturas sucias. En Serializable usa SSI y puede devolver errores de serialización que la aplicación debe reintentar (PostgreSQL Global Development Group, 2024).

Nota sobre MySQL (InnoDB)

InnoDB usa Repeatable Read como nivel predeterminado. Las lecturas simples leen una instantánea consistente, y las lecturas con bloqueo (SELECT ... FOR UPDATE) aplican bloqueos de siguiente clave (next-key locks) que impiden insertar filas en los huecos del rango y así reducen los fantasmas (Oracle Corporation, 2024).

Tema 4.5

4.5 Commit y rollback

Las sentencias de control de transacciones (TCL) delimitan cuándo comienza una transacción y si sus cambios se vuelven permanentes o se descartan. Con ellas el programador aplica en la práctica la atomicidad y la durabilidad. Los ejemplos usan una tabla cuentas(id, titular, saldo) con sintaxis de PostgreSQL.

BEGIN

Inicia un bloque transaccional explícito. A partir de aquí, los cambios no son visibles para otros usuarios hasta confirmarse. Equivale a START TRANSACTION.

BEGIN;
UPDATE cuentas SET saldo = saldo - 500 WHERE id = 1;
-- el cambio aún es provisional

COMMIT

Confirma la transacción: los cambios se vuelven permanentes y visibles, y se liberan los bloqueos.

BEGIN;
UPDATE cuentas SET saldo = saldo - 500 WHERE id = 1;
UPDATE cuentas SET saldo = saldo + 500 WHERE id = 2;
COMMIT;  -- transferencia completa y durable

ROLLBACK

Aborta la transacción y deshace todos los cambios realizados desde el BEGIN, devolviendo la base al estado anterior.

BEGIN;
DELETE FROM cuentas WHERE saldo = 0;
-- se borraron más filas de las esperadas
ROLLBACK;  -- ninguna fila fue eliminada

SAVEPOINT

Marca un punto intermedio dentro de la transacción. Con ROLLBACK TO SAVEPOINT se deshace solo lo posterior a la marca, sin abortar la transacción completa.

BEGIN;
UPDATE cuentas SET saldo = saldo - 500 WHERE id = 1;
SAVEPOINT antes_abono;
UPDATE cuentas SET saldo = saldo + 500 WHERE id = 99; -- cuenta equivocada
ROLLBACK TO SAVEPOINT antes_abono;
UPDATE cuentas SET saldo = saldo + 500 WHERE id = 2;
COMMIT;

Modo autocommit

Si no se escribe BEGIN, la mayoría de los clientes (psql, MySQL) trabajan en modo autocommit: cada sentencia es una transacción independiente que se confirma automáticamente. Por eso, cuando varias operaciones deben cumplirse juntas, es obligatorio agruparlas en un bloque explícito.
